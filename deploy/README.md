# Production: сборка и установка готового комплекта

Приложение работает через Gunicorn и PostgreSQL 17. Статика включена в образ
и отдаётся WhiteNoise; внешних CDN нет. EVA используется через импорт/экспорт
файлов и ссылки в браузере пользователя, без фоновых запросов из приложения.

Сборка, скачивание зависимостей и обновление баз сканеров выполняются на отдельной
машине. На сервер передаются файлы готового выпуска.
Защитные настройки и границы проверок: [SECURITY.md](SECURITY.md).

## Подготовка окружения

Администраторы заранее предоставляют Linux, Docker Engine/Compose, Python 3
(стандартная библиотека для проверки поставки) и OpenSSL для проверки подписи.
Compose должен поддерживать pull_policy, depends_on: service_healthy и --wait.
Платформа совпадает с комплектом: по умолчанию linux/amd64.

Для закрытого контура согласуются корпоративный reverse proxy/PKI, приватная сеть
прокси/web, постоянный том БД и запрет исходящего интернета хоста и контейнеров.
Необходимые внутренние DNS/NTP и другие службы разрешаются отдельно.
Автоматическое получение публичных сертификатов требует внешнего доступа.
pull_policy: never запрещает скачивание образов, но не является сетевым экраном.
ОС и Docker/Compose в комплект приложения не входят.

## Сборка вне сервера

Из чистого зафиксированного коммита на машине с Git, Python 3, обновлённым
Docker Engine >=29.8.2 и доступом к реестрам и зависимостям:

    bash deploy/make_release.sh /absolute/output-directory

Сборщик экспортирует исходники через git archive, собирает три образа с тегами
полного SHA коммита, проверяет PostgreSQL, состав app и отсутствие SQLite,
затем создаёт Trivy-отчёты, SBOM и контрольные суммы.
Для gzip обоих образов дополнительно собирается совместимый с их Debian-базой
пакет с полным upstream-исправлением LZH. Проверяются его слои/хеши, распаковка,
инициализация PostgreSQL из .sql.gz и восстановление сжатого SQL-дампа.
Отчёты находятся в security/*-gzip-build.txt и security/*-gzip-runtime.txt.
Perl образа PostgreSQL пересобирается под Debian 12 с backport-исправлениями
Archive::Tar и четырёх форматтеров Pod::Text. Отчёты security/postgres-perl-build.txt
и security/*-perl-runtime.txt связывают патчи, тесты, пакеты и хеши модулей.
В обоих образах также перенесены оба официальных regex-патча CVE-2026-15534,
с сохранением ABI и полными Debian static/shared тестами. Проверяются 301
граничный случай арифметики, два отрицательных контроля и 8 реальных regex-сценариев.
security/*-perl-regex-build.json и *-perl-regex-runtime.txt связывают исходники,
патчи, нативные тесты и упакованные/запущенные ELF-файлы.
В APP отдельно проверяется отсутствие этих необязательных модулей во всех слоях.
Статус дополнения Archive::Tar и границы проверок описаны в SECURITY.md.
Для опционального Caddy обновлены chi/x/net/go-jose v4. В go-jose v3 перенесены
официальные исправления RSA/JWK, пустого CBC-HMAC ciphertext и глубины JSON.
Проверяются полные suites v3/v4, четыре отрицательных контроля и ограниченные
пробы исходников и фактического vendor-кода. Доказательство связано с бинарным
файлом в security/caddy-jose.json. Сырые High/Medium остаются в JSON/SBOM;
границы технического решения по backport описаны в SECURITY.md.

Базовые образы закреплены digest в deploy/images.env; Python-зависимости —
версиями и SHA256 в requirements.production.txt. Исходники сохраняют права
0644/0755 даже при umask 077. App работает от UID/GID 10001.

| Параметр | Назначение |
| --- | --- |
| RELEASE_PLATFORM | Платформа; по умолчанию linux/amd64 |
| RELEASE_PULL=1 | По умолчанию: запросить базовые образы по закреплённым ссылкам |
| RELEASE_PULL=0 | Использовать уже загруженные базы с теми же digest |
| RELEASE_TLS_COMPAT=1 | Временный профиль совместимости сетевых шагов сборки с сохранением проверки сертификатов/хешей |

RELEASE_PULL=0 не делает сборку автономной: зависимости и базы сканеров всё ещё
могут скачиваться. Параметры применяются только на сборочной машине.
TLS-профиль не переносится в окружение рабочих контейнеров.

Результат — каталог score-it-FULL_COMMIT_SHA: images.tar, images.tsv, VERSION,
release.env, Compose-файлы, шаблон окружения, load_release.sh, verify_release.py,
шаблон Caddy, README.md, SECURITY.md, security/ с отчётами/SBOM и SHA256SUMS.

Для согласованной подписи выпуска на сборочной машине:

    bash deploy/sign_release.sh /absolute/release-directory /private/signing-key.pem

Приватный ключ хранится отдельно. Доверенный публичный ключ передаётся
администраторам независимым согласованным способом.

## Передача и загрузка без интернета

Передайте готовый каталог разрешённым способом. Git-репозиторий и сборочные
инструменты на сервере не нужны. Для новой установки используйте /opt/score-it;
при обновлении сохраняйте рабочий каталог и постоянные настройки.

В каталоге выпуска:

    bash load_release.sh

Для подписанного выпуска:

    bash load_release.sh /absolute/trusted-public-key.pem

Проверяются подпись (когда передан ключ), SHA256 файлов, платформа, конфигурации
и слои загруженных образов. Временные локальные экспорты удаляются после проверки;
нужно свободное место размером с наибольший образ. Контейнеры не запускаются,
БД не изменяется.

Для рабочих и maintenance-сервисов задан pull_policy: never.
Отсутствующий образ приводит к ошибке. На сервере не выполняются make_release.sh,
docker build/pull, установка пакетов или обновление баз Trivy/Scout.

## Постоянные параметры

Для новой установки создайте .env.production из .env.production.example с mode
0600. При обновлении сохраняйте текущие имена БД/ролей, пароли и DJANGO_SECRET_KEY.
Секреты не входят в Git, образы и комплект выпуска.

release.env содержит образы конкретного выпуска и передаётся вторым --env-file.

| Параметры | Назначение |
| --- | --- |
| POSTGRES_DB | Имя рабочей БД |
| POSTGRES_USER / POSTGRES_PASSWORD | Администратор PostgreSQL; в web не передаётся |
| DB_USER / DB_PASSWORD | Runtime-роль без административных и DDL-прав |
| DB_MIGRATION_USER / DB_MIGRATION_PASSWORD | Роль миграций; в web не передаётся |
| DJANGO_SECRET_KEY | Постоянный секрет Django |
| DJANGO_ALLOWED_HOSTS | Имена хостов через запятую |
| DJANGO_CSRF_TRUSTED_ORIGINS | Разрешённые HTTPS origins через запятую |
| SCORE_IT_PROXY_NETWORK | Сеть существующего прокси |
| WEB_WORKERS / WEB_THREADS | Параметры Gunicorn; по умолчанию 2/2 |

Роли и пароли администратора, приложения и миграций различаются.
Имя существующего тома БД и имя Compose-проекта сохраняются при обновлении.
В стандартной установке том называется score-it_postgres_data.

## Первое развёртывание

Пример рассчитан на подготовленный reverse proxy и его сеть.
Определите Bash-функцию с постоянным набором Compose/env-файлов:

    cd /opt/score-it
    compose() {
        docker compose --env-file .env.production --env-file release.env -f compose.production.yaml -f compose.maintenance.yaml -f compose.proxy.yaml "$@"
    }

Затем:

    compose config --quiet
    compose up -d --pull never --no-build --wait db
    compose run --rm --no-deps --pull never db-admin python deploy/configure_db_roles.py
    compose run --rm --no-deps --pull never db-admin python deploy/configure_db_roles.py --apply
    compose run --rm --no-deps --pull never migrate
    compose run --rm --no-deps --pull never web python manage.py check_database_security
    compose up -d --pull never --no-build --wait web

db-admin без --apply показывает план; --apply назначает роли и права.
Миграции выполняет отдельный сервис migrate. Для новой пустой БД:

    compose run --rm --no-deps --pull never web python manage.py createsuperuser

Web получает alias score-it-web в SCORE_IT_PROXY_NETWORK.
PostgreSQL остаётся в закрытой backend-сети без опубликованного порта.
Образ и Compose запускают БД от 999:999 без capabilities, с read-only rootfs и
tmpfs для /tmp и сокета. Для нового именованного тома Docker копирует правильные
права из образа. Существующий том/bind mount должен заранее принадлежать 999:999;
проверьте владельца и доступность всего PGDATA до остановки рабочей БД. Entry point
больше не исправляет root-владельца автоматически. Данные не удаляются и новый
том вместо существующего при обновлении не создаётся.
Web/db имеют встроенные image healthcheck; Compose также проверяет готовность.
Заданы пределы процессов и ротация логов; RAM/CPU выбираются по нагрузке.

## HTTPS и существующий прокси

Caddyfile.score-it.example содержит маскирование access/error logs, предел тела
11 МиБ, ранний 413 и deferred Referrer-Policy: strict-origin.
Другой прокси должен сохранять эти ограничения и корректные Host/X-Forwarded-Proto.

Шаблон Caddy по умолчанию использует публичные сертификаты; в банке TLS
настраивается под корпоративную PKI. Образ Caddy поставляется отдельно и
автоматически не запускается. compose.caddy-image.yaml задаёт образ и
защищённый запуск существующего сервиса caddy: read-only rootfs, tmpfs /tmp,
cap_drop: ALL, no-new-privileges, предел процессов и ротацию логов; скачивание
образа запрещено. Новый образ запускается
от 10002:10002. Перед его выбором проверьте права существующих /data/caddy и
/config/caddy: ранее root-томам потребуется отдельный согласованный перенос прав
с резервной копией. Не удаляйте сертификаты и не меняйте владельца общих томов
без проверки других сайтов. Встроенной универсальной проверки здоровья Caddy
нет; HTTPS-маршруты и срок сертификатов контролируются снаружи.

Для общего прокси проверяются оба сайта, сертификаты, порты, сети и тома.
Второй прокси на занятых портах не создаётся. Настройки других приложений
не заменяются шаблоном Score-it.

## Обновление

Соберите и проверьте новый выпуск, передайте его и выполните load_release.sh.
Сохраните рабочие .env.production, имя проекта, том БД и настройки прокси.
В окно обновления остановите входящие изменения и web; после выбора нового
release.env используйте ранее определённую функцию compose:

    compose stop web
    compose up -d --pull never --no-build --wait db
    compose run --rm --no-deps --pull never migrate
    compose run --rm --no-deps --pull never web python manage.py check_database_security
    compose up -d --pull never --no-build --wait web

Перед переходом на PostgreSQL без XML/JIT/LDAP выполняются
postgres_feature_preflight.sql и проверки данных, сортировок и индексов.
Preflight требует административного доступа для чтения pg_hba_file_rules и
останавливает установку при LDAP-правилах или ошибках разбора HBA, включая
подключённые файлы. Значения правил и LDAP-пароли в вывод не попадают.
Дополнительно проверьте внешние клиенты и их pg_service.conf/PGSERVICEFILE:
клиентская libpq этого образа больше не поддерживает LDAP lookup параметров.
Штатный web использует явные параметры БД; корпоративный вход в веб-приложение
через AD/Keycloak настраивается отдельно от LDAP-аутентификации PostgreSQL.
Переход на другую major-версию PostgreSQL — отдельная процедура.
Возврат старого образа приложения возможен только при совместимости схемы БД:
образ не откатывает миграции и новые записи. Для обычного обновления не применяется
docker compose down -v, удаляющий постоянные тома.

Перенос между окружениями выполняется отдельно: manage.py transfer_data поддерживает
export/import/verify с сохранением ID, проверкой SHA256 и предварительным DRY_RUN;
import --apply принимает пустое назначение. Файлы переноса содержат пользовательские
данные и секреты доступа, поэтому не включаются в Git или публичную поставку.

## Приёмка

Проверьте healthy web/db, check_database_security, HTTPS /healthz/ и /login/,
статику, вход, закрытие голосования, импорт штатного CSV/XLSX и экспорт.

Требование ИБ о закрытом контуре проверяется с заблокированным исходящим интернетом
хоста и контейнеров: загрузка выпуска, первый запуск, перезапуск и рабочие сценарии.
Сетевые журналы должны подтверждать отсутствие запрещённых обращений.
Сама локальная сборка этого не доказывает.
