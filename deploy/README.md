# Production и поставка в закрытый контур

Приложение запускается готовым образом через Gunicorn, PostgreSQL 17 — отдельным
контейнером. Runtime не выполняет `pip install`, `git pull`, сборку или скачивание
образов. Статические файлы включены в образ и отдаются WhiteNoise. В шаблонах нет
внешних CDN. Ссылки EVA открываются браузером пользователя; доступность самой EVA
определяется сетью окружения.

## Требования и конфигурация

Нужны Linux, Python 3 (только стандартная библиотека для проверки комплекта),
Docker Engine и Compose с поддержкой `pull_policy`, `depends_on:
service_healthy` и `--wait`. Комплект по умолчанию собирается для `linux/amd64`;
архитектура сервера должна совпадать. Docker/Compose устанавливаются администраторами
до переноса. Образ приложения работает от UID/GID 10001, с read-only rootfs и /tmp.

Рабочий каталог на новом сервере: `/opt/score-it`. Создайте `.env.production` на
основе `.env.production.example`, права `0600`. Заполните пароли, Django key,
ALLOWED_HOSTS и CSRF origins для своего домена. Для сохранения действующих сессий
при переносе сохраните `DJANGO_SECRET_KEY` исходного сайта. Не отправляйте этот
файл в чат, Git, образ или архив релиза. `POSTGRES_USER/POSTGRES_PASSWORD` —
администратор отдельного экземпляра PostgreSQL score-it. `DB_USER/DB_PASSWORD` —
отдельная runtime-роль; `DB_MIGRATION_USER/DB_MIGRATION_PASSWORD` — отдельная роль
миграций. Имена ролей и пароли должны различаться. Пароли администратора и миграций
не передаются web. Порт БД не публикуется. Порядок обновления существующей БД и
общего Caddy описан в [SECURITY.md](SECURITY.md).

Compose создаёт постоянный том `score-it_postgres_data`. Замена образа приложения
не меняет его содержимое. Не используйте `docker compose down -v`.

`release.env` содержит точные имена образов данного релиза и передаётся вторым
`--env-file`; `.env.production` содержит постоянные настройки окружения.

## Сборка комплекта вне закрытого контура

На машине с Git, Docker, Python 3 и доступом к registry/PyPI, из чистого коммита:

```bash
bash deploy/make_release.sh /absolute/output-directory
```

По умолчанию сборка принудительно запрашивает базовые образы из реестра
(`RELEASE_PULL=1`). Если образы уже загружены, но повторное получение метаданных
реестра обрывается, для стандартного Docker builder можно использовать локальные
образы с теми же закреплёнными digest:

```bash
. deploy/images.env
for IMAGE in "$PYTHON_SOURCE_IMAGE" "$POSTGRES_SOURCE_IMAGE" "$GO_SOURCE_IMAGE" "$CADDY_SOURCE_IMAGE"; do
  docker pull --platform "${RELEASE_PLATFORM:-linux/amd64}" "$IMAGE"
done
RELEASE_PULL=0 bash deploy/make_release.sh /absolute/output-directory
```

Этот режим требует наличия всех четырёх базовых образов локально и SHA256 в их
ссылках. Он отключает только принудительный `--pull` при сборке; загрузка пакетов
Python/Go/Alpine и базы Trivy по-прежнему требует сети. Сканирование, создание SBOM
и контрольных сумм выполняются в обычном порядке.

Если загрузка образов работает, но `apk` внутри сборки выдаёт TLS-ошибку, можно
явно включить профиль совместимости для сетевых шагов сборки:

```bash
RELEASE_PULL=0 RELEASE_TLS_COMPAT=1 bash deploy/make_release.sh /absolute/output-directory
```

По умолчанию `RELEASE_TLS_COMPAT=0`. Режим `1` выбирает обычные ECDH-группы для
OpenSSL и отключает гибридный ML-KEM в Go только на время `apk`, Git, Go и запуска
Trivy. Проверка сертификатов, подписей APK, хешей Python и Go-модулей сохраняется.
Профиль OpenSSL создаётся во временном файле и удаляется после команды, включая
её неуспешное завершение. В готовых контейнерах нет `OPENSSL_CONF`/`GODEBUG` этого
профиля; настройки TLS Caddy и PostgreSQL не меняются. Использованные параметры
сборки записываются в `security/build-options.txt` и входят в `SHA256SUMS`.
Этот флаг не настраивает Docker daemon на машине сборки: если сброс возникает
при самом `docker pull`, совместимость клиента и демона нужно настроить отдельно.
Справка: https://go.dev/doc/godebug и
https://docs.openssl.org/3.5/man3/SSL_CTX_set1_curves/.

Скрипт требует обновлённый сборочный Docker (>=29.8.2), собирает код через
`git archive`, получает PostgreSQL 17 и пересобирает Caddy с исправленными Go/x/net.
Все три образа получают теги с полным SHA коммита и сохраняются в `images.tar`.
Сканирование точных образов, SBOM и результаты находятся в `security/`. Найденные
секреты или High/Critical в Go/x/net Caddy останавливают выпуск. В каталоге релиза
также находятся Compose-файлы, шаблон настроек, `release.env`, `images.tsv` с ID
конфигураций образов, `VERSION`, `load_release.sh`, `verify_release.py`, эта инструкция
и `SHA256SUMS`. Конфигурации включают digests несжатых слоёв; отображаемый Docker
image ID не используется как переносимая идентичность, поскольку classic storage
и containerd показывают разные типы ID.
PostgreSQL имеет собственный тег score-it, поэтому загрузка релиза не меняет теги
образов других проектов. ОС/архитектура и ID сохранены в манифесте.

Платформа задаётся `RELEASE_PLATFORM` (по умолчанию `linux/amd64`). Идентичности
базовых образов закреплены digest в `deploy/images.env`; изменение фиксируется
коммитом и требует повторной сборки/сканирования. Пакеты Python закреплены версиями
и SHA256; pip обновляется при сборке и исключается из runtime-образа.
Переход на другую major-версию PostgreSQL требует отдельной процедуры переноса;
нельзя подключать существующий том PostgreSQL 17 к другой major-версии.

## Загрузка без интернета

Передайте каталог комплекта разрешённым способом и разместите его файлы в
`/opt/score-it` (не заменяя существующий `.env.production`). Это файлы выпуска,
а не исходный Git-репозиторий. Проверьте согласованную контрольную сумму поставки.

```bash
cd /opt/score-it
bash load_release.sh
```

Скрипт проверяет SHA256 файлов, выполняет `docker image load` и сверяет точные байты
конфигурации, платформу и digests слоёв загруженных образов с переданным архивом.
Для проверки используются временные локальные экспорты образов (требуется свободное
место размером с наибольший образ); после проверки временные файлы удаляются.
Исходный комплект и контейнеры проверкой не изменяются.
Он не запускает приложение и не меняет БД. Для всех сервисов установлено
`pull_policy: never`: отсутствующий образ приводит к ошибке вместо скачивания.

Далее в примерах используется массив:

```bash
cd /opt/score-it
COMPOSE=(docker compose --env-file .env.production --env-file release.env -f compose.production.yaml -f compose.maintenance.yaml)
```

### Первое развёртывание / назначение для переноса

Запустите только новую базу и создайте структуру таблиц:

```bash
"${COMPOSE[@]}" up -d --pull never --no-build --wait db
"${COMPOSE[@]}" run --rm --no-deps --pull never db-admin python deploy/configure_db_roles.py
"${COMPOSE[@]}" run --rm --no-deps --pull never db-admin python deploy/configure_db_roles.py --apply
"${COMPOSE[@]}" run --rm --no-deps --pull never migrate
"${COMPOSE[@]}" run --rm --no-deps --pull never web python manage.py check_database_security
```

До импорта не запускайте web и не создавайте суперпользователя: база должна быть
пустой, кроме служебных типов объектов и разрешений, созданных Django migrate.

## Перенос всех данных SQLite → PostgreSQL

Требуется одинаковая версия кода и применённых миграций на исходном и новом сайте.
Перед экспортом этого релиза установите зависимости и выполните `migrate` также
на исходном сайте: добавлены служебные таблицы django-axes, схема источника и
назначения должна совпадать. Исходный SQLite-путь должен быть проверен
отдельно: на shared-хостинге это
`/private/score-it/db.sqlite3`.

Команда экспортирует все управляемые модели: пользователей с хешами паролей,
группы, права и M2M, сессии Django, admin log, проекты, задачи, спринты, ресурсы,
приглашения, комнаты, участников, токены, очереди, раунды и голоса.
ID, временные метки и все поля сохраняются. Неизвестные таблицы или неприменённые
миграции останавливают перенос. Таблица истории миграций создаётся `migrate`, а
служебные content types/permissions переносятся с исходными ID в одной транзакции.
В текущих моделях нет FileField/ImageField; если они появятся, загруженные файлы
потребуется переносить отдельно.

Рабочие Docker-образы поддерживают только PostgreSQL: из них удалены SQLite и
Python-модули `sqlite3`/`_sqlite3`. В образе приложения закреплены
`DB_ENGINE=postgresql` и `SCORE_IT_REQUIRE_POSTGRESQL=1`; попытка выбрать SQLite
завершается понятной ошибкой до создания файлов. Исходники и обычная установка
через `requirements.txt` сохраняют поддержку SQLite для разработки и экспорта
со старого хостинга. Выполняйте SQLite-экспорт на исходном сервере, как в пункте 3;
в Docker-контуре работают импорт/экспорт/проверка JSON через PostgreSQL.

Сборка удаляет пакеты через APT без обновлений, загрузок и autoremove. Допустимый
план удаления ограничен явно: `libsqlite3-0` в приложении; `libsqlite3-0`, `gpg`,
`gnupg`, `gpg-wks-client` и `gpg-wks-server` в PostgreSQL. Другой план останавливает
сборку. Версии PostgreSQL, glibc/ICU и параметры постоянного тома сохраняются.
Проверка каждого слоя обоих сохранённых образов и runtime-проверка Python входят
в `make_release.sh`, результат — `security/sqlite-payload.txt` в контрольных суммах
комплекта. Обнаружение SQLite в инвентаре Trivy блокирует выпуск.

1. Сначала проведите репетицию в отдельной пустой базе. Исходный сайт может
   работать: экспорт получает согласованный read-only снимок транзакцией SQLite.
   Изменения после начала снимка попадут только в окончательный перенос.
2. Для окончательного переноса включите режим обслуживания на старом хостинге,
   остановите все запросы и фоновые процессы, которые могут писать в БД, дождитесь
   завершения текущих запросов. Держите старый сайт закрытым для записи в течение
   переключения DNS. Обычный `touch .restart-app` не является остановкой записи.
3. На исходном сервере из каталога приложения:

   ```bash
   .venv/bin/python manage.py transfer_data export \
     --file /private/score-it/transfer-final.json
   ```

   Команда только читает исходную БД, создаёт новый файл с правами `0600`, не
   перезаписывает существующий файл и печатает SHA256 и количества по моделям.
   Содержимое содержит хеши паролей и ключи сессий: не размещайте файл внутри www,
   не коммитьте и не отправляйте в чат.
4. Передайте файл по SSH/SCP в `/opt/score-it/transfer/transfer-final.json` на
   новый сервер, сохранив закрытые права доступа. При одноразовом запуске команда
   внутри контейнера выполняется от UID пользователя сервера, чтобы прочитать файл
   `0600`; rootfs контейнера остаётся read-only. Каталог монтируется только для чтения.
5. На новом сервере укажите SHA из экспорта:

   ```bash
   TRANSFER_SHA=SHA256_ИЗ_ЭКСПОРТА
   TRANSFER_ARGS=(run --rm --no-deps --pull never --user "$(id -u):$(id -g)" \
     -v /opt/score-it/transfer:/transfer:ro migrate python manage.py transfer_data)
   "${COMPOSE[@]}" "${TRANSFER_ARGS[@]}" import \
     --file /transfer/transfer-final.json --expected-sha256 "$TRANSFER_SHA"
   ```

   Это DRY_RUN: проверяет файл, схему, миграции и пустоту назначения. Он не
   гарантирует успешное приведение значений до фактической загрузки в PostgreSQL.
6. Импорт и отдельная проверка:

   ```bash
   "${COMPOSE[@]}" "${TRANSFER_ARGS[@]}" import \
     --file /transfer/transfer-final.json --expected-sha256 "$TRANSFER_SHA" --apply
   "${COMPOSE[@]}" "${TRANSFER_ARGS[@]}" verify \
     --file /transfer/transfer-final.json --expected-sha256 "$TRANSFER_SHA"
   ```

   Ожидаются `IMPORT_VERIFIED`, затем `VERIFY_OK`. APPLY блокирует таблицы,
   повторно проверяет пустоту и загружает данные в одной транзакции. Проверяются
   внешние ключи и SHA256 содержимого каждой модели, включая M2M, затем выставляются
   последовательности ID. При несовпадении транзакция отменяется. Повторная загрузка
   в уже заполненную БД запрещена. Проверка не выводит персональные данные.
7. Запустите web сначала для локальной проверки через SSH-туннель:

   ```bash
   "${COMPOSE[@]}" -f compose.local-test.yaml up -d --pull never --no-build --wait web
   ```

   С локального компьютера: `ssh -L 18000:127.0.0.1:18000 USER@SERVER`.
   Для полноценного браузерного входа с secure cookies используйте тестовый HTTPS
   маршрут через Caddy; не отключайте secure cookies на рабочем домене ради проверки.
   Сверьте вход со старым паролем, проекты, оценки, составы спринтов, ресурсы,
   комнаты, историю голосов, ссылки и импорт EVA.
8. После проверки настройте Caddy и домен. Старый сайт остаётся закрытым для записи,
   пока возможны обращения по старому DNS. До разрешения записей в новой БД можно
   вернуться на исходный сайт. После новых записей в PostgreSQL простой возврат
   на старую SQLite потеряет эти изменения: потребуется отдельное согласование данных.

## Существующий Caddy / сервер KidsTime

Для web используйте дополнительно `-f compose.proxy.yaml`. Web получает alias
`score-it-web` в сети `score_it_proxy`; PostgreSQL остаётся только в закрытой
backend-сети. Caddy тоже должен быть подключён к `score_it_proxy`, причём эта сеть
должна быть объявлена в его постоянной Compose-конфигурации.

Будущий маршрут Caddy (после проверки фактического Caddyfile):

```caddyfile
score-it.example.com {
    reverse_proxy score-it-web:8000
}
```

Не поднимайте второй контейнер на занятых портах 80/443. Изменения Compose/Caddyfile
KidsTime выполняются отдельно после просмотра конфигурации; одной временной команды
`docker network connect` недостаточно для сохранения сети после пересоздания Caddy.
Финальная конфигурация web использует proxy override без local-test override.

В банке можно подключить web к согласованному корпоративному reverse proxy.
Автоматическое получение публичных сертификатов требует внешнего доступа; в закрытом
контуре используются корпоративные сертификаты/TLS termination банка. Если нужен
отдельный контейнер прокси, его образ и конфигурация включаются в комплект поставки
отдельно. Этот комплект содержит также исправленный Caddy, но не запускает его
автоматически: его подключают к существующему Compose прокси либо используют
корпоративный reverse proxy банка.

## Следующие релизы

Соберите новый комплект с новой версией образа, передайте и загрузите его. На время
обновления остановите web (и доступ к записи), выполните `migrate` одноразовым
сервисом `migrate`, затем запустите web с `--pull never --no-build --wait`.
Перенос данных `transfer_data import` повторно не выполняется. PostgreSQL major не
меняется вместе с обычным релизом приложения. Сохранение предыдущего образа само по
себе не откатывает миграции БД; совместимость возврата проверяется для каждого релиза.

Для приёмки в банке проверьте установку и работу с заблокированным исходящим
интернетом. Поставка не включает ОС, Docker/Compose и корпоративные сертификаты.
